## Web 安全面试笔记

这篇笔记按漏洞类型和面试场景整理，方便复习时直接按模块背：原理、特征、判断方式、修复思路。

## Web 黑盒基础

### 常见漏洞类型

黑盒测试里常见的 Web 漏洞包括：

- SQL 注入
- XSS
- XXE
- SSRF
- CSRF
- CORS 配置问题
- RCE
- 越权 / IDOR
- 未授权访问
- 逻辑漏洞
- 弱口令
- OAuth 认证缺陷
- 文件上传
- 文件包含
- 中间件漏洞

面试回答时可以按三层说：漏洞原理、流量或行为特征、修复方式。

## SQL 注入

### 原理

SQL 注入出现在数据交互过程中。前端参数传到后端后，如果后端没有严格校验或参数化处理，而是把用户输入直接拼接进 SQL 语句，输入内容就可能被数据库当作 SQL 语句的一部分执行。

### 常见类型

- 字符型注入
- 数字型注入
- 布尔盲注
- 时间盲注
- 报错注入
- 联合查询注入
- 堆叠查询注入
- 宽字节注入
- XFF 等请求头注入

### 常见报错函数

MySQL 报错注入里常见函数：

- `extractvalue`
- `updatexml`
- `floor`

这些函数常被用来制造数据库错误回显，面试时重点说明它们属于报错注入特征即可。

### SQL 注入流量分析

判断流量中是否存在 SQL 注入，可以看请求包里是否有典型数据库操作特征：

- 查询数据库版本，例如 `version`
- 查询库名、表名、字段名，例如 database、schema、table、column 等关键词
- 联合查询关键词
- 报错函数特征
- 布尔条件特征
- 延时函数特征
- 注释符、拼接符、编码绕过痕迹

判断是否攻击成功时，要对比请求包和响应包：

- 响应里是否出现数据库报错、版本信息、表名、字段名。
- 页面内容是否随着布尔条件变化。
- 是否出现符合延时盲注特征的响应时间变化。
- 是否有后续异常数据库访问、文件写入或主机行为。

只有请求里有 payload 但响应无执行痕迹时，更像攻击尝试；如果响应能证明语句被执行，则倾向于攻击成功。

### sqlmap 高低 level 区别

sqlmap 的不同 level 主要区别在于测试范围和 payload 数量：

- level 越高，测试的参数位置越多。
- payload 数量更多，覆盖面更广。
- 请求数量增加，速度更慢，也更容易产生噪声。
- 高 level 可能测试 Cookie、User-Agent、Referer 等位置。

面试可以答：低 level 快、影响小；高 level 覆盖更全，但更慢、更容易触发告警。

### SQL 注入写文件条件

SQL 注入写文件需要同时满足多项条件：

- 数据库账号具备文件写入权限。
- 知道或能推断 Web 绝对路径。
- 数据库进程对目标目录有写权限。
- Web 服务能访问并解析写入的文件。
- 目标目录没有禁止脚本执行。

常见相关能力点：

- `outfile` 更适合写文本类结果或导出数据。
- `dumpfile` 可写原始内容。
- `file_put_contents` 是 PHP 层面的文件写入函数，不属于数据库原生写文件能力。

### `-os-shell` 原理概念

`sqlmap -os-shell` 的核心思路是：在授权测试环境中，如果注入点具备写文件条件，工具可能尝试把一个服务端脚本写入 Web 可访问目录，再通过这个脚本转发命令执行结果，形成交互式命令执行能力。

面试重点：

- 依赖数据库文件写入权限。
- 通常需要 Web 绝对路径。
- 需要 Web 服务可访问并解析写入脚本。
- 高权限数据库账号或错误配置会放大风险。

防护重点：

- 业务数据库账号最小权限。
- 禁止数据库进程写 Web 目录。
- Web 目录和上传目录禁止脚本执行。
- 参数化查询，不拼接 SQL。
- 对异常 SQL 行为和文件写入行为做监控。

### 修复

- 使用预编译 / 参数化查询。
- 使用 ORM 或 PDO 等安全接口。
- 对输入做类型校验和白名单限制。
- 数据库账号最小权限。
- 禁止业务账号写文件、执行高危函数。
- 统一错误处理，不把数据库报错直接返回给用户。
- 配合 WAF、日志审计和告警监控。

预编译原理：预编译会先把 SQL 模板交给数据库解析，再把参数作为数据传入执行。参数不会被当作 SQL 语法解析，因此可以有效防止注入。

## XSS

### 原理

XSS 是由于服务端或前端没有对用户输入做充分过滤、转义或上下文编码，导致脚本被插入页面并在用户浏览器中执行。

### 类型

- 存储型 XSS：恶意内容写入数据库或持久化存储，用户访问相关页面时触发。
- 反射型 XSS：恶意内容通过 URL 或请求参数反射到页面，需要诱导用户访问。
- DOM 型 XSS：主要发生在前端 DOM 操作中，不一定经过服务端。

### 告警判断

看到 XSS 告警时，可以这样判断是否成功：

- 请求中是否包含脚本、事件属性、危险标签或编码后的脚本。
- 响应正文是否原样或解码后反射了脚本。
- 保存响应为 HTML，在安全隔离环境中观察是否触发脚本行为。

### 修复

- 按输出上下文进行 HTML / JS / URL 编码。
- 使用白名单过滤危险标签和属性。
- 避免直接把用户输入写入 `innerHTML`。
- Cookie 开启 `HttpOnly`、`Secure`、`SameSite`。
- 配置 CSP。
- 对富文本使用成熟安全库处理。

## XXE

### 原理

XXE 是 XML 外部实体注入。应用解析 XML 时，如果允许加载外部实体，可能导致文件读取、内网探测、SSRF 或拒绝服务等风险。

### 特征

- 请求体里出现 XML。
- 出现 `DOCTYPE`、`ENTITY`、`SYSTEM`、`PUBLIC` 等关键词。
- 响应或日志中出现本地文件内容、外部请求记录或解析异常。

### 防御

- 在 XML 解析器层面禁用外部实体。
- 禁用 DTD。
- 过滤或拒绝 `DOCTYPE`、`ENTITY`、`SYSTEM`、`PUBLIC` 等危险结构。
- 尽量使用 JSON 等更简单的数据格式。
- 限制解析器访问文件系统和网络。

## SSRF

### 原理

SSRF 是服务器端请求伪造。攻击者利用服务端发起请求的能力，让服务器替自己访问内网、云元数据地址、本地服务或其他非预期资源。

### 特征分析

常见流量特征：

- 请求参数中出现 URL、IP、回调地址、图片抓取、远程资源加载等字段。
- 出现 `@`、`#`、短链接、跳转、编码混淆等 URL 混淆特征。
- 访问 `localhost`、`127.0.0.1`、内网 IP、云元数据地址。
- 出现 `dict`、`gopher`、`file` 等异常协议。
- 出现 IP 进制转换、域名解析绕过、重定向链等痕迹。

### 无明显回显时如何判断

如果可以做授权验证：

- 看目标是否向外部检测地址发起请求。
- 查 DNS、HTTP、代理、出网日志是否有记录。
- 查服务端日志是否访问内网、云元数据地址或异常协议。

如果无法复现，则结合流量交互、服务端日志和安全设备日志综合判断。

### 防护

- 使用 URL 白名单。
- 禁止访问内网地址、环回地址、链路本地地址和云元数据地址。
- 限制协议，只允许必要的 `http` 和 `https`。
- 禁止自动跟随重定向，或重定向后重新校验目标。
- 统一出网代理并记录审计日志。

## CSRF

### 原理

CSRF 是攻击者盗用用户已登录状态，以用户名义向目标站点发送非预期请求。它利用的是浏览器自动携带 Cookie 的机制。

### 类型

- GET 型
- POST 型
- JSONP 型

### SSRF 与 CSRF 区别

- CSRF：利用用户浏览器和登录态，让用户替攻击者发请求。
- SSRF：利用服务器发请求能力，让服务器替攻击者访问资源。

### 防护

- 校验 CSRF Token。
- 校验 `Origin` / `Referer`。
- 关键操作二次确认或验证码。
- Cookie 设置 `SameSite`。
- 高危接口不要只依赖 Cookie 鉴权。

## XSS、CSRF、XXE 的区别

- XSS：服务端或前端对用户输入过滤、转义不足，导致脚本在用户浏览器执行。
- CSRF：服务端没有充分校验请求是否来自用户真实意愿，攻击者利用用户 Cookie 伪造请求。
- XXE：XML 解析器允许加载外部实体，导致文件读取、内网探测、拒绝服务等风险。

## CORS 配置问题

### 原理

CORS 问题通常来自跨域策略配置过宽，比如允许任意来源读取敏感接口响应，导致浏览器同源策略被错误放宽。

### 简单请求与非简单请求

- 简单请求：通常是 `GET`、`HEAD`、部分 `POST`，且 `Content-Type` 满足特定条件。
- 非简单请求：会先发送 `OPTIONS` 预检请求，再发送正式请求。

### 修复

- 严格限制 `Access-Control-Allow-Origin`。
- 不要对敏感接口使用通配符来源。
- 凭证请求必须严格校验来源。
- 使用 Token、Referer / Origin 白名单等方式辅助控制。
- 配合 CSRF 防护。

## RCE 与命令执行

### 原理

RCE 是远程代码执行。应用把不可信输入拼接到代码、命令、模板、表达式或反序列化流程中，可能导致攻击者控制服务端执行逻辑。

### 告警判断

看到命令执行告警时：

- 看请求包是否包含系统命令特征。
- 看响应包是否出现命令执行结果，例如系统信息、网络配置、用户信息。
- 如果无回显，结合日志、进程、文件变更、网络连接进一步确认。

### 修复

- 不拼接系统命令。
- 使用安全 API 替代命令调用。
- 参数白名单和类型校验。
- 最小权限运行应用。
- 使用沙箱或容器隔离。
- 对危险函数和异常进程行为做监控。

## 越权与逻辑漏洞

### 越权 / IDOR

越权是应用没有正确限制用户访问权限，导致用户能访问或操作不属于自己的资源。

常见类型：

- 水平越权：同等级用户之间越权访问。
- 垂直越权：低权限用户访问高权限功能。

修复：

- 每个接口都做服务端鉴权。
- 资源访问必须绑定当前用户身份。
- 管理员接口和普通接口分权。
- 重要操作加二次确认和审计日志。

### 逻辑漏洞

逻辑漏洞不一定来自技术缺陷，而是业务流程设计存在问题。

常见类型：

- 支付金额篡改。
- 重放攻击。
- 权限提升。
- 找回密码流程缺陷。
- 注册、验证码、频率限制缺陷。
- 越权访问或越权操作。

修复重点是梳理业务流程，在服务端做完整状态校验、权限校验和幂等控制。

### 登录框怎么渗透

授权测试中可关注：

- 弱口令。
- 注册和找回密码逻辑。
- 越权访问。
- 验证码或频率限制缺陷。
- CMS 版本和公开漏洞。

### 登录后台后怎么办

授权测试中可关注：

- 上传点。
- 插件、模板、主题、附件管理等可写位置。
- 框架和中间件版本。
- 后台功能是否存在越权、文件操作、命令执行等风险。

## 文件上传漏洞

### 原理

文件上传功能没有对上传文件进行严格验证和过滤时，攻击者可能上传非预期文件，尤其是可被服务器解析执行的动态脚本文件，从而造成高风险后果。

形成条件：

1. 存在文件上传点。
2. 上传文件类型、内容或后缀校验不足。
3. 上传目录具有不合理的执行权限。
4. 上传后的文件能被外部访问。

### 可能危害

- 上传恶意脚本，获取 Web 权限。
- 覆盖、污染或伪造业务文件。
- 配合解析漏洞、文件包含漏洞扩大影响。
- 成为后续横向移动或持久化入口。

### 上传数据包关注点

文件上传流量中常看：

- `Content-Length`：上传内容大小。
- `MAX_FILE_SIZE`：前端声明的最大上传大小，不能作为安全边界。
- `Filename`：上传文件名和后缀。
- `Content-Type`：上传文件 MIME 类型。
- 文件正文内容：是否含脚本、木马、危险函数或异常结构。

### 服务端检测点

- MIME 类型。
- 文件后缀。
- 文件真实内容。
- 文件大小。
- 文件名安全性。
- 存储路径和访问权限。

### 常见绕过思路与防护表达

面试中可以按“绕过思路 + 防护方式”回答：

- MIME 类型绕过：只看 `Content-Type` 不可靠，防护应以服务端内容识别为准。
- 后缀大小写绕过：统一大小写后再校验。
- 空格绕过：规范化文件名，去除危险字符。
- 双写绕过：不要依赖简单替换，使用白名单。

推荐防护：

- 使用白名单校验文件类型和后缀。
- 文件重命名，避免保留用户原始文件名。
- 上传目录禁止脚本执行。
- 文件存储到 Web 根目录外，通过下载接口读取。
- 对文件内容做魔数校验和安全扫描。
- 限制大小、数量、频率，并记录审计日志。

### 文件上传告警如何判断是否成功

- 看响应状态码，404 类告警可优先降低优先级，但不能只看状态码。
- 看响应是否 200、302 或返回上传成功信息。
- 看请求中文件名是否为危险脚本后缀或伪装后缀。
- 看文件内容是否包含脚本、危险函数或异常结构。
- 看上传后文件是否可访问、是否被解析执行。

## 文件包含漏洞

### 原理

文件包含漏洞通常出现在应用使用 `include`、`include_once`、`require`、`require_once` 等函数动态包含文件时。如果包含路径受用户输入影响，且没有做好白名单限制，就可能包含非预期文件。

分类：

- 本地文件包含 LFI：包含服务器本地文件。
- 远程文件包含 RFI：包含远程资源，通常依赖危险配置。

### 函数区别

- `include`：文件不存在时通常产生警告，程序继续运行。
- `require`：文件不存在时通常产生致命错误，程序停止运行。
- `include_once` / `require_once`：只包含一次，避免重复加载。

### 防护

- 禁止用户直接控制包含路径。
- 使用固定映射表或白名单。
- 禁止远程包含配置。
- 对路径做规范化，防止目录穿越。
- 最小化 Web 服务文件读取权限。

## 未授权访问

### 原理

未授权访问是指攻击者不需要认证或授权，就能访问系统敏感资源或高危功能。常见原因包括默认配置、弱认证、访问控制缺失、管理面暴露等。

### Redis 未授权

修复：

- 设置认证口令。
- 绑定内网地址，不暴露到公网。
- 使用防火墙限制访问来源。
- 禁止高危命令或进行命令重命名。
- 最小化 Redis 运行权限。
- 监控异常连接、异常写入和配置变更。

风险概念：

Redis 未授权可能导致数据泄露、配置篡改、持久化文件写入、计划任务风险或横向移动风险。面试中重点说明风险链路和修复方式，不建议记忆具体攻击步骤。

### JBoss 未授权

管理面板如果没有鉴权或鉴权不严，可能导致部署、配置修改或敏感信息泄露。修复应关闭公网暴露、启用强认证、限制管理入口来源并升级版本。

## 常见中间件漏洞

### 常见类型

- IIS：PUT 漏洞、短文件名猜解、远程代码执行、解析漏洞。
- Apache：解析漏洞、目录遍历。
- Nginx：解析配置不当导致脚本解析问题。
- Tomcat：弱口令、管理后台部署风险、解析漏洞。
- JBoss：反序列化漏洞、管理后台未授权、部署风险。
- WebLogic：反序列化漏洞、SSRF、任意文件上传、后台部署风险。
- Apache Shiro：RememberMe 反序列化相关风险。

### Shiro

- Shiro-550：常与固定密钥、RememberMe 反序列化链路相关。
- Shiro-721：与 CBC 模式和 Padding Oracle Attack 相关。
- 流量特征：请求或响应中可能出现较长的 `rememberMe` 字段，异常情况下可能出现删除或异常 rememberMe 行为。

### Struts2

- 某些历史漏洞与内容类型解析、OGNL 表达式执行、参数映射等机制有关。
- 特征可能出现在请求参数、`Content-Type`、OGNL 表达式片段或应用日志中。
- 防护重点是升级版本、禁用危险配置、最小化暴露入口、结合日志排查。

### Fastjson

- 根因常与 AutoType 机制、反序列化类型控制不严有关。
- 流量中可能出现 `@type`、异常类名、JNDI 相关字段等特征。
- 修复应升级安全版本、关闭 AutoType、使用白名单、避免直接反序列化不可信 JSON。

### Log4j

- Log4j2 历史高危问题与 Lookup/JNDI 解析能力有关。
- 特征可能包括日志或请求字段中出现 JNDI 相关字符串。
- 修复应升级安全版本、移除危险组件、关闭相关解析能力，并排查历史日志。

## 告警流量分析

### 总体判断方法

看到告警后不要只看规则名，要结合请求、响应和主机侧证据判断：

- 请求包是否带有 Top 10 常见漏洞特征。
- 响应包是否证明执行成功。
- 是否有主机侧进程、文件、账号、计划任务、网络连接变化。
- 安全设备是否有多条关联告警。
- 是否能形成完整时间线。

### SQL 注入告警

看请求中是否有 SQL 语句、数据库函数、注释符、联合查询等特征；再看响应中是否有数据库报错、版本信息、表名字段名或内容差异。

### 命令执行告警

看请求中是否有系统命令特征；再看响应中是否出现命令执行结果。如果没有回显，需要结合日志、进程、文件变更和网络连接确认。

### XSS 告警

看请求中是否有脚本、事件属性、危险标签；再看响应正文是否反射脚本，并在安全隔离环境中验证是否触发。

### SSRF 告警

如果无明显回显，重点看出网日志、DNS 解析、HTTP 访问日志、云元数据访问痕迹和代理日志。

### 文件上传告警

看状态码、返回内容、文件名、文件内容、落地路径、是否可访问、是否被解析执行。

## HVV 与应急响应

### HVV 前准备

常见准备：

- 资产收集。
- 版本和补丁检查。
- 弱口令排查。
- 文件和目录梳理。
- 安全设备策略检查。
- 员工安全意识培训。
- 日志采集和留存策略确认。

### CS 反制概念

防守视角重点看：

- 诱饵和蜜罐。
- 对批量上线行为做进程、网络、文件和域名监测。
- 对可疑样本做隔离分析，不在生产环境直接执行。
- 结合 EDR、NDR、WAF、IDS/IPS 等设备联动。

### 安全设备

常见设备：

- IDS / IPS
- 入侵检测 / 入侵防御
- WAF
- 防火墙
- 蜜罐
- EDR
- NGAF

### 防火墙如何使用

面试表达：

- 看告警流量，分析是否误报。
- 对误报量大的规则进行策略优化。
- 对确认攻击来源加入黑名单或临时封禁。
- 对业务必要流量设置白名单。
- 和客户或业务方确认策略影响，避免误伤。

## 溯源

常见溯源方向：

- 审查钓鱼邮件。
- 获取安全设备数据，尤其是流量数据。
- 查看网络资产所在服务器运行状态。
- 查看中间件和应用日志。
- 汇总攻击 IP、域名、样本、User-Agent、时间线、请求路径等 IOC。
- 合理使用蜜罐系统进行溯源追踪。
- 根据应急响应中获得的信息综合判断攻击者基础设施。

面试可以说：溯源不只靠单点证据，要把流量、主机、日志、样本、账号行为和时间线串起来。

## 挖矿木马处置

### Linux

排查思路：

- 查看高 CPU 进程。
- 确认进程 PID、启动路径和父进程。
- 查看网络连接和异常端口。
- 查看计划任务、启动项、历史命令。
- 隔离样本并备份证据。
- 停止恶意进程，清理落地文件和持久化项。
- 修复入口漏洞，避免清完后再次上线。

常见命令方向：

- `top`：查看资源占用。
- `ps`：查看进程。
- `netstat` / `ss`：查看连接和端口。
- `crontab`：查看计划任务。
- `history`：查看历史命令。

### Windows

排查思路：

- 打开资源管理器或任务管理器，查看 CPU 占用高的服务和进程。
- 打开文件所在位置，判断是否属于异常程序。
- 先备份可疑样本，再进行隔离和清理。
- 关闭对应服务与进程。
- 删除对应计划任务、启动项、注册表残留。
- 重启后复查进程、服务、计划任务和网络连接。

常见命令方向：

- `tasklist`：查看进程。
- `netstat -an`：查看端口。
- `services.msc`：查看服务。
- `eventvwr.msc`：查看日志。
- `lusrmgr.msc`：查看账号。

## 应急响应常用命令与分析

### Linux

- `ps -aux`：查看进程。
- `netstat -antlp`：查看端口。
- `top`：查看 CPU 使用情况。
- `crontab`：查看计划任务。
- `history`：查看历史命令。

### Windows

- `tasklist`：查看进程。
- `netstat -an`：查看端口。
- `services.msc`：查看服务。
- `eventvwr.msc`：查看日志。
- `lusrmgr.msc`：查看账号。

### 有告警怎么分析是否是攻击

- 看请求包里面是否带有 Top 10 漏洞特征。
- 看响应包是否证明执行成功。
- 看是否有主机侧进程、文件、账号、计划任务、网络连接变化。
- 看安全设备是否有多条关联告警。
- 看是否能形成完整时间线。

### 怎么做应急响应

基本流程：

1. 确认告警和影响范围。
2. 保留证据，避免直接破坏现场。
3. 隔离受影响主机或账号。
4. 排查日志、端口、进程、文件、计划任务、启动项、注册表、账号。
5. 清理恶意文件和持久化项。
6. 修复入口漏洞和弱口令。
7. 恢复业务并持续监控。
8. 输出复盘报告和加固建议。

## Web 白盒补充

白盒审计时重点关注：

- 用户输入进入 SQL、命令、模板、反序列化、文件路径、URL 请求的位置。
- 权限校验是否在服务端完成。
- 文件上传、文件读取、文件包含路径是否可控。
- XML、JSON、表达式、模板等解析器是否安全配置。
- 日志是否记录关键操作，是否泄露敏感信息。
- 第三方组件版本是否存在已知漏洞。

白盒和黑盒的区别在于：白盒能看到代码路径和数据流，适合定位根因；黑盒更偏请求响应和外部行为验证。
